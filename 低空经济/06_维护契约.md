# 低空经济行业知识库 — 维护契约

> 本文件是 `低空经济/` Vault 的维护宪法。所有 LLM Agent 与人工维护者在 Vault 内创建、更新、链接、归档页面时，必须遵守本契约。
> 与本契约冲突的页面以本契约为准；变更契约须在 `09_操作日志.md` 追加变更记录，并在 `04_运维报告/` 存档影响评估。
> 设计意图来源：`docs/superpowers/specs/2026-07-19-低空经济行业知识库-design.md`。本契约是可执行规则；二者冲突时以设计规格为准并据此修订本契约。

## 0. 契约适用范围与不可越界原则

- 本契约仅约束 `低空经济/` Vault 内的维护行为。
- **不可越界**：维护者不得创建或修改 Vault 内本契约、`03_模板/` 模板、被任务显式指派的知识页面以外的既有文件。原始资料层 `02_原始资料/` 为只读存档，禁止覆盖或删除。
- 不提交 git、不修改 `.obsidian/` 配置，除非任务显式授权。

## 2. Frontmatter 规范（完整定义）

每个知识页面**必须**以 YAML frontmatter 开头，且**必须**包含以下字段。缺失任一必填字段视为结构不完整。

```yaml
---
# —— 基础字段（必填）——
title: ""                      # 页面人类可读标题，与正文 H1 一致
type: industry | player | customer | pain_point | keyword | opportunity | validation | synthesis | source | framework | tracker | glossary | risk | workload | system | map | route
status: seed | growing | mature
industry: 低空经济
market: 中国
research_purpose: 投资研究
evidence_level: low | medium | high

# —— 时间字段（必填）——
created: YYYY-MM-DD            # 创建日期，写入后不变
updated: YYYY-MM-DD            # 最近一次实质性更新
data_as_of: YYYY-MM-DD        # 页面内关键数据的数据截止时点

# —— 关联字段（必填）——
tags: []                       # Obsidian 标签，用于检索
aliases: []                    # 别名，便于双链匹配（如公司曾用名/简称）
related: []                    # 关联页面文件名列表（不含路径），≥2 项

# —— 来源字段（必填）——
source_url: ""                 # 主来源 URL；无独立来源留空
sources: []                    # 全部引用来源标识或 URL

# —— 行动字段（必填）——
next_action: ""                # 下一步维护或验证行动
owner: ""                      # 维护负责人；空表示待认领

# —— 结论三态标记（必填）——
verify_status: fact | inference | unverified
---

# 公司页（type: player）额外字段
listed: true | false                       # 是否上市
ticker: ""                                 # 上市代码（A股/港股/美股）
stage: 业绩兑现型 | 订单验证型 | 适航或产品验证型 | 基础设施受益型 | 主题映射型
order_maturity: L1 | L2 | L3 | L4 | L5     # 代表性订单成熟度，见 §5
cert_progress: []                          # 适航与运营资质进度，见 §6
```

### 2.1 字段取值规则

- `type`、`status`、`evidence_level`、`verify_status` 等枚举字段只能取规定值，禁止自造。
- `evidence_level` 是**判断与来源强度**的约束，不代表页面主题的重要程度（见 §3）。
- `verify_status` 是页面整体主结论的三态标记；页面内每条声明仍须按 §4 逐条标注，不可仅凭页面级标记免责。
- `related` 必须列**文件名**（不含路径与 `.md`），且对应文件真实存在；空数组或仅 1 项视为链接不完整。
- `data_as_of` 必须反映页面内最新数据的真实截止日，不是页面写作日；二者不同时分别记录。
- 未取得数据的字段保留占位空值（`""`、`[]`），并在正文显式说明"数据缺失"，禁止用零或推断值填充。

## 3. 证据等级体系（low / medium / high）

### 3.1 三级定义

| 等级 | 定义 | 典型来源 |
| --- | --- | --- |
| `high` | 监管文件、适航文件、审计年报、交易所公告、国家标准、官方统计 | 民航局适航文件、上市公司年报、国务院文件 |
| `medium` | ≥2 个可靠来源相互印证，或有清晰数据口径的权威研究 | 券商研报 + 公司公告互证、行业协会统计 |
| `low` | 单一媒体、企业宣传、专家预测、研究者基于公开信息的推断 | 自媒体、企业新闻稿、AI 推断 |

### 3.2 来源优先级（高 → 低）

1. 国务院、民航局、工信部等政府和监管文件
2. 国家标准、适航审定信息和官方统计
3. 上市公司年报、公告和投资者关系材料
4. 企业官网、产品手册和正式新闻稿
5. 行业协会、研究机构和有数据口径的券商报告
6. 权威媒体
7. 自媒体和社交媒体，仅作为待验证线索（不得作为确定结论唯一来源）

### 3.3 升级与冲突规则

- **禁止自动升级**：单一来源永远不得自动升级为确定结论，即便该来源是企业官方宣传。
- 证据等级随来源增减而**动态调整**：新来源出现互证可上调；来源被撤销或互证破裂须下调。
- 数据冲突时**同时记录来源及口径差异**，优先采用高等级来源，并在冲突解决前下调结论置信度、在 `verify_status` 上倾向 `unverified` 或在正文标注 `[待验证]`。

## 4. 事实 / 推断 / 待验证 三态标注

页面内每一条实质性声明都必须可被归入以下三态之一，并以规定语法显式标注。无标注的确定性声明是知识库健康隐患。

| 三态 | 含义 | 证据要求 | 标注语法 |
| --- | --- | --- | --- |
| 事实 (fact) | 已被 high/medium 来源确认的客观数据或已发生事件 | 必须附来源 URL/出处 | `> [事实]` 引用块，或行内 `**事实**：` 前缀 |
| 推断 (inference) | 基于事实的合理推论或分析判断，尚未被独立来源证实 | 附证据等级 + 推理依据 | `> [推断]` 引用块，注明依据 |
| 待验证 (unverified) | 无可靠来源支撑的假设、线索或预期 | 无须来源，但须列入待验证节 | `> [待验证]` 引用块，列入"待验证问题"节 |

### 4.1 章节归属

- **核心事实**节只放 `事实`；放不进来的内容移到推断或待验证。
- **投资含义或合理推断**节放 `推断`。
- **待验证问题**节放 `待验证`，并给出验证行动与预期来源。
- 一句话判断可混合三态，但含推断/待验证时必须在句尾标注，例如："某公司处于订单验证阶段（推断）"。

### 4.2 绝对化语言禁令

- 禁止对 `推断` 与 `待验证` 内容使用"已实现""已确认""必然""将"等绝对化措辞。
- 规划、预测、意向订单与已实现数据须分属不同三态，不得混写。

## 5. 订单成熟度 L1–L5

意向订单、框架协议、确定订单与已交付订单必须分级标注，禁止把意向或框架直接当作确定订单或已实现收入。

| 级别 | 名称 | 定义 | 法律/会计特征 |
| --- | --- | --- | --- |
| L1 | 意向（Intent） | 意向函、备忘录（MOU）、合作声明 | 无法律约束力，可随时退出 |
| L2 | 框架协议（Framework） | 框架协议或战略合作协议，约定意向规模与价格区间 | 部分约束，常含生效条件 |
| L3 | 确定订单（Firm Order） | 正式采购合同，确定数量、价格、交付节奏与付款条款 | 法律约束力强，但尚未交付 |
| L4 | 排产/交付中（In Delivery） | 进入卖方生产计划或已开始物理交付 | 存在可核验交付节点 |
| L5 | 已交付/确认收入（Delivered & Recognized） | 已交付并经买方验收，按会计准则确认收入 | 理想情形含回款证据 |

### 5.1 标注要求

- 订单条目须写明 `级别`、`数量`、`对方`、`披露时点`、`来源`；缺失项标"未披露"。
- 公司页 `order_maturity` frontmatter 字段填**代表性订单**的当前级别；多订单分列时取最高成熟度。
- L3 及以上才能进入"确定订单"汇总；L1/L2 须单独统计，不得与 L3 合并报数。
- L5 与"确认收入"对应，但二者口径不同：L5 是交付与验收事件，确认收入还须满足会计准则收入确认条件（见 §7）。

## 6. TC / PC / AC / OC 适航与运营资质口径

eVTOL 与航空器资质链必须按以下口径区分，禁止把型号认证等同于单机适航或运营资质。

| 缩写 | 全称 | 层级 | 含义 |
| --- | --- | --- | --- |
| TC | Type Certificate / 型号合格证 | 型号设计级 | 证明某型号航空器**设计**符合适用适航标准；取得 TC 才能进入量产与单机适航阶段 |
| PC | Production Certificate / 生产许可证 | 生产体系级 | 证明制造商**生产体系与质量控制系统**符合要求，能稳定批量生产符合 TC 设计的航空器 |
| AC | Airworthiness Certificate / 适航证 | 单机级 | 证明**某一架具体航空器**符合经 TC 批准的型号设计并处于安全可用状态 |
| OC | Operating Certificate / 商业运营资质 | 运营人级 | 证明运营人具备安全商业运营该类航空器的能力与组织体系；中国涵盖通用航空经营许可与运行合格证（AOC）等 |

### 6.1 阶段顺序与易混淆点

- 标准顺序：TC（设计定型）→ PC（量产能力）→ AC（单机适航）→ OC（商业运营）。
- 取得 TC 不等于取得 PC，更不等于取得 AC 或 OC；任何"已获认证"表述须指明是哪一证。
- 试验飞行适用**特许飞行证**，不计入上述四证；健康检查须区分试验飞行与适航飞行。
- 海外对标（如 FAA Type Certificate、EASA）须标注监管体系差异，不直接套用中国口径。

## 7. 其他易混淆口径

对以下叙事必须显式检查和标注，禁止混用：

### 7.1 市场规模

- 须标明**统计范围、基期、预测年份**与是否含上游零部件。
- 地方产业规划目标或签约金额不得直接视为已实现市场规模。
- 预测值标注 `[推断]` 或 `[待验证]`，不得与历史实际值同列而不区分。

### 7.2 合同额 / 收入 / 回款 / 利润贡献

- **含税合同额** ≠ **确认收入** ≠ **回款** ≠ **利润贡献**。
- 公司页须分列：合同额（L3 起披露）、确认收入（L5 + 会计准则）、回款、利润贡献；缺失项标"数据缺失"。
- 禁止用合同额替代收入或用收入替代利润。

### 7.3 规划目标 vs 实际投资

- 地方规划目标、签约项目与实际完成投资分属不同三态；规划目标标 `[待验证]` 或 `[推断]`。
- 禁止把规划目标年份的预测当作当年实际数据。

### 7.4 公司整体营收 vs 低空相关业务营收

- 必须区分公司整体营收与低空相关业务营收、利润。
- 主题映射型公司尤其须标注低空业务的实际关联与收入利润贡献；无公开数据时明确写"数据缺失"，不得用融资宣传替代经营数据。

### 7.5 财务数据口径

- 财务期间与口径必须一致（同为年报或同为半年报、同为合并或母公司）。
- 标明币种、单位（亿元/万元）与期间；更新时保留历史对比，不用新值直接覆盖旧值。

## 8. 只追加日志规则

### 8.1 只追加文件清单

以下文件/目录为**只追加**，禁止修改、删除或覆盖历史内容：

- `09_操作日志.md`
- `05_知识库/08_验证/` 下的验证日志
- `05_知识库/12_跟踪器/` 中的历史快照表（新增行/列，不改旧值）

### 8.2 日志条目格式

`09_操作日志.md` 每条一行，格式：

```
- YYYY-MM-DD HH:mm | 类型 | 影响范围 | 摘要 | 操作者
```

类型枚举：`init`（初始化）、`ingest`（资料摄入）、`update`（内容更新）、`verify`（验证结论变更）、`health`（健康检查）、`reconcile`（口径冲突处理）、`contract`（契约变更）。

### 8.3 数据更新规则

- 保留历史对比值：新增行/列记录新值与时点，不用新值直接覆盖旧值。
- 跟踪器更新历史快照时追加新行，旧行保留。
- 发现历史错误时**追加更正条目**并指向原条目，**不修改原文**；原条目标注"已被更正见 YYYY-MM-DD 条目"。

## 9. 双链与导航规则

### 9.1 双链语法

- Obsidian `[[双链]]` 只引用**文件名**（不含路径、不含 `.md`），重命名目录不影响双链。
- 关联页面优先用双链，不用裸 URL；URL 仅用于来源出处。

### 9.2 关联要求

- 每个知识页 `related` ≥2 项且对应文件真实存在。
- 禁止孤立页面：任何知识页必须可从 `07_导航首页.md`、`08_索引.md` 或其他页面双链抵达。
- 政策、技术、公司、场景、指标、投资判断之间须建立交叉双链，避免互不连接的资料集合。

### 9.3 导航与索引同步

- 新增/删除页面后同步更新 `08_索引.md`（一句话摘要）与 `07_导航首页.md`（数据快照/系统状态）。
- `08_索引.md` 须覆盖全部知识页面；健康检查以索引覆盖率衡量。

## 10. 健康检查规则

### 10.1 检查清单

交付与定期维护须执行以下检查：

1. **结构完整性**：所有知识页含完整 frontmatter（§2）；最小页面集完整；维护契约/导航/索引/日志存在且与实际目录一致。
2. **链接完整性**：所有 `[[双链]]` 指向存在页面；每页 ≥2 有效关联；无孤立页面。
3. **证据完整性**：确定性数据可追溯来源；未证实判断标注为推断或待验证；规划/预测/意向订单与已实现数据区分；财务数据标明期间/单位/口径。
4. **口径一致性**：订单 L1–L5（§5）、TC/PC/AC/OC（§6）、市场规模/收入/利润（§7）标注无误。
5. **全局一致性**：`07_导航首页.md` 页面数/来源数/最近更新与实际一致；`08_索引.md` 覆盖全部页面；`09_操作日志.md` 记录初始化/填充/健康检查。

### 10.2 频率与存档

- 每轮深度填充后、每季度、或知识库"显得混乱/不完整/难扩展"时运行健康检查。
- 报告以 `YYYY-MM-DD-health-check.md` 命名存入 `04_运维报告/`，不覆盖历史报告。
- 发现缺陷须在 `09_操作日志.md` 追加 `health` 条目并跟踪修复。

## 11. 页面写作规范

- **短节优先**：用一句话判断、核心事实、推断、关键指标、关联页面、待验证、下一步、来源等短节；不写长报告。
- **中文为主**，技术术语保留英文（如 eVTOL、TC、AOC）。
- **避免绝对化语言**，对推断与待验证内容尤其严格（§4.2）。
- **数据必须标注来源**，无来源的确定性声明标 `[待验证]`。
- **财务数据**标明期间、单位、口径、币种（§7.5）。
- 非上市公司明确"无完整公开财务数据"边界，不用未经验证的融资宣传替代经营数据。

## 12. 变更与版本管理

- **契约变更**：修改本契约须在 `09_操作日志.md` 追加 `contract` 条目，说明变更点与影响页面，并在 `04_运维报告/` 存档影响评估。
- **模板变更**：修改 `03_模板/` 须同步更新引用该模板的页面说明，并追加 `update` 日志。
- **页面重命名**：重命名知识页须同步更新所有双链与 `08_索引.md`，并在日志记录新旧名。
